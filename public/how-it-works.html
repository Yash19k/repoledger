How it works

What happens between GitHub and your dashboard

RepoLedger is one small Node server, one PostgreSQL database, a read-only GitHub App and a collector that runs every six hours. This page walks through each part: what it asks GitHub for, what it stores, for how long, and how it is protected.

Two ways to use it

GitHub only shares a repository's traffic with people who can push to it. So RepoLedger has two modes: anyone can look up public statistics, and only the owner, signed in, sees traffic.

Look up a username

/u/<login> · no sign-in

Reads a user's public repositories with RepoLedger's own token and caches the results.

  • Stars with full history, weekly commits and lines changed
  • Open and closed issues and pull requests, top contributors
  • Never views, clones or referring sites

Sign in as the owner

/ · GitHub sign-in + app install

You install the GitHub App on the repositories you choose, and RepoLedger collects their traffic.

  • Everything a lookup shows, plus daily views, unique visitors and clones
  • Referring sites and popular pages, private repositories you select
  • Shown only to you while signed in

The moving parts

The browser loads a plain HTML, CSS and JavaScript app from public/; there is no build step. Everything else goes through one Express server (server.js). A separate collector process (src/collector.js) runs on a schedule and shares the same database and GitHub client code.

The collector and the server never talk to each other directly. They meet in the database. The server can also start a collection itself, right after a first sign-in or when you press Collect now.

A public lookup, step by step

Opening /u/octocat serves the same single page as the landing page. The script sees the username in the address and asks the server for /api/public/octocat.

  1. Cache check. If RepoLedger read this account in the last six hours, the cached result comes back at once.
  2. Background refresh. Otherwise the server starts a refresh and answers refreshing with progress. The page polls every two seconds and shows a progress bar.
  3. Which repositories. The refresh lists repositories the account owns (up to 500, most recently pushed first), drops forks and private ones, and keeps the 60 most recently pushed.
  4. Per repository, four at a time: weekly commits and lines added and removed, contributors, today's star count, open and closed issues and pull requests, and, the first time a repository with up to 2,000 stars is seen, its full star history rebuilt from each stargazer's timestamp.
  5. Ready. The next poll returns the profile and its repositories, and the dashboard asks /api/public/octocat/data for the chosen date range.

Lookups use a GitHub token with no scopes (GITHUB_PUBLIC_TOKEN), which can only read public data. GitHub allows it 5,000 requests an hour, shared by every visitor, so RepoLedger rations it:

  • At most three lookups run at once. A fourth visitor sees Waiting for a free slot and the page retries every five seconds.
  • Each network may start 30 new lookups an hour. Opening cached results doesn't count.
  • A lookup stops when the hourly budget falls to its reserve (10% of GitHub's limit, at most 300 requests), so one huge account can't use up everyone else's lookups or sign-ins.
  • If the account doesn't exist, the answer is "not found" and any cached copy is deleted.

Lookups never include traffic. The public endpoints only query commit, issue, star and contributor tables, and only for repositories in that profile's own cached list. A repository that its owner's installation reports as private is hidden from lookups even if it was public when cached.

Signing in

Sign-in uses the GitHub App's own OAuth flow. RepoLedger only needs to learn who you are and which installations of the app belong to you, so the token GitHub hands back is used for two requests and then revoked.

Solid arrows are requests, dashed arrows are responses. Steps 7 to 11 all happen inside the single /auth/callback request.

  1. State. /auth/login creates 16 random bytes, stores them in a short-lived cookie scoped to /auth, and sends you to GitHub with the same value. The callback compares the two in constant time, which stops another site from completing a sign-in in your browser.
  2. Who you are. The code is exchanged for a user token, which reads your GitHub id, login and avatar, and your installations of the app. Only installations on your own personal account are recorded; organisations aren't supported yet.
  3. Revoked. Whatever happens, the user token is revoked at the end of the request. RepoLedger never stores it.
  4. First collection. If an installation has never been collected, a collection starts in the background, so your dashboard fills within a minute or two.

After you install or change the app on GitHub, GitHub sends you to /auth/installed, which simply signs you in again to pick up the change.

The GitHub App and its permissions

RepoLedger is a GitHub App, not a classic OAuth app. You see the exact permissions on GitHub's install screen, and you choose all repositories or only some. Every permission is read-only.

PermissionAccessWhy
AdministrationReadGitHub requires it for the traffic API: views, clones, referrers and popular pages. RepoLedger uses it for nothing else.
IssuesReadOpen and closed issue counts.
Pull requestsReadOpen and closed pull-request counts.
MetadataReadRepository names. Every GitHub App has it.
ContentsNot requestedRepoLedger can never read your code or files.

The app has no webhook. Instead, the collector notices when an installation disappears or a repository is removed from it, and deletes the matching data.

Two kinds of app tokens

App token (JWT)
Signed with the app's private key (RS256), valid for about nine minutes. It can only list installations and ask for installation tokens.
Installation token
Issued by GitHub for one installation, valid for an hour, limited to the repositories you picked. Kept in memory and reused until five minutes before it expires.

Sessions

Once GitHub has confirmed who you are, RepoLedger keeps you signed in with its own session, not with a GitHub token.

  • Random token, stored hashed. The session token is 32 random bytes. Your browser holds the token; the database holds only its SHA-256 hash, so a database leak doesn't hand out working sessions.
  • Cookie flags. rl_session is HttpOnly (scripts can't read it), SameSite=Lax, and Secure whenever the site runs on HTTPS.
  • 30 days. Sessions expire after 30 days. Signing in again replaces your old session instead of leaving it valid, signing out deletes it, and expired rows are cleaned up every hour.
  • Every request hashes the cookie and looks it up. If the database is down you get a "try again" error, not a silent sign-out.

How traffic outlives GitHub's 14 days

GitHub's traffic API only ever returns the last 14 days: one row per day of views and of clones, with totals and unique visitors. RepoLedger asks for those 14 days every six hours and saves each day as its own row, keyed by repository and date.

  • Overlap is the point. Each run rewrites the days GitHub still reports, so a day's numbers settle on GitHub's final count. Days that have fallen out of GitHub's window stay in the database untouched.
  • Missed runs are harmless as long as one run succeeds within any 14-day stretch. Only a gap longer than that loses days.
  • Referring sites and popular pages are different: GitHub only gives a top-10 summary of the last 14 days, not daily rows, so RepoLedger keeps the latest summary and replaces it on each run.

One collection run

  1. GitHub Actions starts npm run collect at minute 0 of every sixth hour (UTC). Two runs never overlap, and a run is stopped after 60 minutes.
  2. With the app token, it lists every installation of the app and deletes the data of installations that are gone.
  3. Installations are sorted least recently collected first, so a run cut short starts with whoever was skipped, and four are collected in parallel (each has its own GitHub rate limit).
  4. For each installation it lists the repositories you granted, deletes data for repositories you removed, then reads every repository: views, clones, referrers and popular pages, plus the same public stats a lookup collects.

Collect now in the account menu runs the same code inside the web server. It is refused if your data was collected in the last 10 minutes, and can be started at most once a minute, because every run spends the app's shared GitHub rate limit.

The lookup cache can't grow forever

Every hour the server deletes cached lookups that:

  • nobody has opened for 30 days (a view is recorded at most once an hour per profile),
  • never finished, unless they are running right now,
  • fall outside the 200 most recently opened.

At roughly 0.2 to 0.7 MB each, that keeps lookups under about 140 MB, so they can't crowd owners' traffic out of a small database. Both limits are settings (PUBLIC_PROFILE_TTL_DAYS, PUBLIC_MAX_PROFILES) on your own deployment.

Leaving

  • Delete my data uninstalls the app through GitHub's API first (so the next collection can't re-create anything), then deletes your installations, their stats, your account and your sessions. A collection running at that moment is cancelled and its writes cleaned up.
  • Uninstalling on GitHub deletes your data on the next collection run.
  • Removing one repository from the installation deletes that repository's traffic on the next run.

Security model and rate limits

The private parts of RepoLedger are your traffic and your session. These rules protect them.

Your repositories only
Owner endpoints answer only for repositories in your own, non-suspended installations. Asking for another repository by name just filters it out.
Strict browser policy
A Content-Security-Policy allows scripts only from RepoLedger itself and images only from itself and GitHub avatars, and blocks framing by other sites.
Cross-site requests
Every state-changing request (sign out, Collect now, Delete my data) must carry RepoLedger's own Origin or Referer.
Nothing cached
API and sign-in responses are marked no-store, so no browser or proxy keeps a copy of private traffic.
Tokens stay home
GitHub tokens are only ever sent to api.github.com, even when following pagination links, and every GitHub request times out after 20 seconds.
Other headers
nosniff, same-origin referrers and opener policy, and HSTS when served over HTTPS. Request bodies are capped at 10 KB.

Rate limits

Limits count per network: an IPv4 address, or an IPv6 /56 block, since one customer usually gets a whole IPv6 range and could otherwise dodge limits by rotating addresses. They are fixed one-minute or one-hour windows held in memory.

Run your own

RepoLedger needs Node.js 20 or newer and a PostgreSQL database. npm run init-db creates the tables, and npm run create-app creates your own GitHub App with the read-only permissions above and saves its keys to .env. A Dockerfile is included for hosting.
